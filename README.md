# Автономный облёт зданий на ArduCopter

Дрон взлетает, летит по прямой к целевой точке, обнаруживает здания лидаром,
облетает их и садится в цели. Реализация — алгоритм **Bug2** в узле ROS 2,
управление через MAVROS, симуляция ArduPilot SITL + Gazebo Harmonic.

Целевая точка задаётся параметром запуска, правка кода не требуется.

**Видео демонстрации:** https://drive.google.com/file/d/1F_XarFJ8MXqkjw09EklaP-_HONLjiJE9/view?usp=drive_link

## Быстрый старт

Если окружение уже установлено:

```bash
./scripts/run.sh              # цель по умолчанию (0, 60)
./scripts/run.sh 25 80        # другая цель: target_x=25, target_y=80
```

Скрипт пересобирает сцену из конфига, переустанавливает пакеты, поднимает
Gazebo, ArduPilot SITL, MAVROS, мост и планировщик.
Останов — `Ctrl+C`, все процессы гасятся автоматически.

Сцена (количество и положение зданий) правится в
`avoidance_sim/config/buildings.yaml`, мир пересобирается при каждом запуске.

## Установка с нуля

Порядок важен: каждый слой ставится и проверяется отдельно.

### 1. ArduPilot + SITL

```bash
cd ~
git clone --recurse-submodules https://github.com/ArduPilot/ardupilot.git
cd ardupilot
Tools/environment_install/install-prereqs-ubuntu.sh -y
. ~/.profile
./waf configure --board sitl && ./waf copter
```

Добавить в `~/.bashrc`:

```bash
export PATH=$PATH:$HOME/ardupilot/Tools/autotest
export PATH=$HOME/.local/bin:$PATH      # здесь лежит mavproxy.py
```

Проверка: `sim_vehicle.py -v ArduCopter --console -w`, затем в MAVProxy
`mode guided` → `arm throttle` → `takeoff 10`.

### 2. Gazebo Harmonic

```bash
sudo curl https://packages.osrfoundation.org/gazebo.gpg \
  --output /usr/share/keyrings/pkgs-osrf-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/pkgs-osrf-archive-keyring.gpg] http://packages.osrfoundation.org/gazebo/ubuntu-stable $(lsb_release -cs) main" \
  | sudo tee /etc/apt/sources.list.d/gazebo-stable.list > /dev/null
sudo apt update && sudo apt install -y gz-harmonic
```

Проверка: `gz sim -v4 -r shapes.sdf`

### 3. Плагин ardupilot_gazebo

```bash
sudo apt install -y libgz-sim8-dev rapidjson-dev libopencv-dev \
  libgstreamer1.0-dev libgstreamer-plugins-base1.0-dev \
  gstreamer1.0-plugins-bad gstreamer1.0-libav gstreamer1.0-gl

cd ~ && git clone https://github.com/ArduPilot/ardupilot_gazebo
cd ardupilot_gazebo && export GZ_VERSION=harmonic
mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=RelWithDebInfo && make -j2
```

В `~/.bashrc`:

```bash
export GZ_VERSION=harmonic
export GZ_SIM_SYSTEM_PLUGIN_PATH=$HOME/ardupilot_gazebo/build:$GZ_SIM_SYSTEM_PLUGIN_PATH
export GZ_SIM_RESOURCE_PATH=$HOME/ardupilot_gazebo/models:$HOME/ardupilot_gazebo/worlds:$GZ_SIM_RESOURCE_PATH
```

`libgz-sim8-dev` — это именно Harmonic. В части руководств встречается
`libgz-sim7-dev` от Garden, с ним плагин не собирается.

### 4. ROS 2 Humble

```bash
sudo apt install -y software-properties-common && sudo add-apt-repository -y universe
export ROS_APT_SOURCE_VERSION=$(curl -s \
  https://api.github.com/repos/ros-infrastructure/ros-apt-source/releases/latest \
  | grep -F "tag_name" | awk -F\" '{print $4}')
curl -L -o /tmp/ros2-apt-source.deb \
  "https://github.com/ros-infrastructure/ros-apt-source/releases/download/${ROS_APT_SOURCE_VERSION}/ros2-apt-source_${ROS_APT_SOURCE_VERSION}.$(. /etc/os-release && echo $VERSION_CODENAME)_all.deb"
sudo dpkg -i /tmp/ros2-apt-source.deb
sudo apt update && sudo apt install -y ros-humble-desktop ros-dev-tools
echo "source /opt/ros/humble/setup.bash" >> ~/.bashrc
```

Подключение репозитория ROS через deb-пакет `ros2-apt-source` — актуальный
способ; инструкции с ручной правкой `sources.list` и ключом `ros.key` устарели.

### 5. MAVROS и мост

```bash
sudo apt install -y ros-humble-mavros ros-humble-mavros-extras \
  ros-humble-mavros-msgs ros-humble-ros-gzharmonic
wget https://raw.githubusercontent.com/mavlink/mavros/ros2/mavros/scripts/install_geographiclib_datasets.sh
chmod +x install_geographiclib_datasets.sh && sudo ./install_geographiclib_datasets.sh
```

Датасеты GeographicLib обязательны, без них `mavros_node` падает при старте.

### 6. Этот репозиторий
Репозиторий обязан лежать внутри `src/` ROS-воркспейса — `run.sh` определяет корень воркспейса как две директории вверх от себя.
```bash
mkdir -p ~/ros2_ws/src && cd ~/ros2_ws/src
git clone <URL этого репозитория> building-avoidance
cd ~/ros2_ws && colcon build --symlink-install
source install/setup.bash
```

### 7. Проверка

```bash
echo $GZ_SIM_RESOURCE_PATH | grep ardupilot_gazebo   # не должно быть пусто
which sim_vehicle.py mavproxy.py                      # оба должны найтись
ros2 pkg list | grep avoidance                        # два пакета
```

Первая строка критична: без пути к моделям `ardupilot_gazebo` сцена откроется
без дрона и без сообщения об ошибке. Переменные из шагов 1 и 3 должны быть
в `~/.bashrc` — новый терминал их подхватит, текущий требует `source ~/.bashrc`.

Полный прогон:

```bash
./scripts/run.sh
```

Ожидаемая последовательность в логе планировщика: `ожидание связи` →
`GUIDED` → `арминг` → `взлёт` → `полёт по m-линии` → `встреча` →
`обход границы` → `цель достигнута` → `посадка`.

## Запуск и параметры

```bash
./scripts/run.sh                    # цель по умолчанию (0, 60)
./scripts/run.sh 0 90              # target_x=0, target_y=90
```

### Необязательное удобство

Чтобы не набирать путь целиком, можно завести алиас:

```bash
echo "alias ba-go='\$HOME/ros2_ws/src/building-avoidance/scripts/run.sh'" >> ~/.bashrc
source ~/.bashrc
```

После этого запуск сокращается до `ba-go` и `ba-go 0 90`. Скрипт определяет
своё расположение сам, поэтому алиас работает из любой директории. На видео
используется именно он — это то же самое, что `./scripts/run.sh`.

`avoidance_planner/config/mission.yaml`, любой переопределяется через
`-p имя:=значение`:

| Параметр | Знач. | Смысл |
|---|---|---|

| `corridor_half` | 2.5 | Полуширина коридора, м |
| `max_range` | 15.0 | Обрезка дальномера, м |
| `mline_tol` | 2.0 | Допуск возврата на m-линию, м |

### Сцена

`avoidance_sim/config/buildings.yaml`:

```yaml
buildings:
  - {name: b1, x: 0.0, y: 25.0, sx: 20.0, sy: 10.0, sz: 15.0}
  - {name: b2, x: 0.0, y: 55.0, sx: 24.0, sy: 10.0, sz: 18.0}
```

`x`, `y` — центр в мировой ENU Gazebo, `sx/sy/sz` — габариты. Мир
`building.sdf` пересобирается генератором `scripts/gen_world.py` при каждом
запуске, поэтому XML править не нужно. Высота зданий выбрана заведомо больше
рабочей высоты полёта: перелететь сверху нельзя по условию.

## Как это работает

```
Gazebo (физика, gpu_lidar)
    │  /scan  (gz.msgs.LaserScan)
    │  /clock (gz.msgs.Clock)
    ▼
ros_gz_bridge
    │  /scan  (sensor_msgs/LaserScan)
    │  /clock (rosgraph_msgs/Clock)
    ▼
avoidance_planner ──────► /mavros/setpoint_velocity/cmd_vel_unstamped
    ▲                     /mavros/set_mode, /cmd/arming, /cmd/takeoff
    │ /mavros/local_position/pose, /mavros/state
    │
MAVROS ◄──MAVLink──► ArduPilot SITL ◄──JSON──► Gazebo (ArduPilotPlugin)
```

Планировщик — конечный автомат:

```
WAIT → MODE(GUIDED) → ARM → TAKEOFF → GO ⇄ AVOID → HOLD → LAND
                                       ↓
                                   FAILSAFE → RTL
```

**GO** — полёт по m-линии (прямой старт→цель). Каждый цикл проверяется коридор
по курсу; при обнаружении препятствия фиксируется точка встречи и сторона
обхода, переход в AVOID.

**AVOID** — движение вдоль границы: направление = касательная к стене
(перпендикуляр к направлению на ближайшую точку) плюс радиальная поправка,
удерживающая расстояние до стены около `clearance`. Уход обратно в GO — по
классическому условию Bug2: снова на m-линии и ближе к цели, чем в точке
встречи.

Частота управляющего цикла — 20 Гц, команда скорости сглаживается фильтром
первого порядка, нос доворачивается по направлению движения (лидар жёстко
закреплён на корпусе, поэтому важно, куда он смотрит).

## Ответы на вопросы задания

### 1. Почему выбран этот способ облёта? Что ещё рассматривалось и почему отклонено?

Выбран **Bug2** — по двум причинам: он даёт формальную гарантию завершения
(при выпуклых препятствиях дрон либо дойдёт до цели, либо докажет её
недостижимость) и при этом объясним целиком, без подбора весов и эвристик.
Однако следует помнить, что Bug2 заведомо не оптимален по длине пути.

Что рассматривалось:

**Встроенное избегание препятствий ArduPilot** (`OA_TYPE` = BendyRuler или
Dijkstra + Proximity). Технически самый короткий путь: подключить лидар как
proximity-источник и настроить параметры. Отклонено как решение задания —
здесь не появляется собственного алгоритмического содержания.
Отдельно отмечу: для реального аппарата это как раз
правильный выбор, потому что избегание работает на уровне автопилота и
переживает потерю связи с бортовым компьютером.

**Потенциальные поля.** Притяжение к цели плюс отталкивание от препятствий,
десяток строк кода. Отклонено из-за локальных минимумов: у плоской стены
силы уравновешиваются, и дрон встаёт — зависание.

**Глобальный планировщик по карте** (A*, RRT* на сетке занятости). Даёт
оптимальный путь, но требует карты — то есть либо предварительного знания
сцены, либо SLAM. Для облёта нескольких коробок это несоразмерно сложно, а
предварительная карта противоречит смыслу задачи («дрон должен увидеть
здание»).

**VFH / follow-the-gap** — реактивные методы без состояния: каждый цикл
строится полярная гистограмма свободных секторов, выбирается ближайший к
направлению на цель. Соблазнительны тем, что у них нет автомата фаз и,
соответственно, целого класса ошибок с переключениями про такие ошибки
см. раздел с проблемами). Отклонены из-за
отсутствия гарантии завершения: на вогнутых препятствиях и U-образных
ловушках реактивный метод зацикливается. Если бы сцена содержала сложные
невыпуклые формы, я бы, вероятно, выбрал именно этот путь и добавил
детектор циклов.

### 2. Как дрон «видит» здание и как решает, куда лететь?

**Датчик.** 2D-лидар кругового обзора (`gpu_lidar` в Gazebo): 180 лучей на
360°, 10 Гц, дальность до 40 м. Закреплён жёстко на корпусе. Плоскость
сканирования горизонтальна в горизонтальном полёте.

**Путь данных.** `gpu_lidar` → `ros_gz_bridge` → `/scan`
(`sensor_msgs/LaserScan`). Лучи приходят в полярных координатах связанной
системы: угол отсчитывается от носа дрона.

**Преобразование.** Для каждого луча с дальностью `r` и углом `a`:

```
θ = yaw + a                          # yaw из /mavros/local_position/pose
p = (x_дрона + r·cos θ,  y_дрона + r·sin θ)
```

Получается облако точек в мировой ENU. Лучи с `r` вне `[range_min, max_range]`
отбрасываются.

**Решение о манёвре** принимается в двух местах:

*Обнаружение (фаза GO).* Строится прямоугольный коридор по направлению на
цель: глубина `detect_dist` = 12 м, полуширина `corridor_half` = 2.5 м. Точка
попадает в коридор, если её проекция вдоль курса лежит в `(0, 12)`, а
поперечное смещение по модулю меньше 2.5. Есть хоть одна такая точка —
коридор занят. Сторона обхода выбирается по знаку среднего поперечного
смещения препятствия: обходим с той стороны, где точек меньше.

*Ведение границы (фаза AVOID).* Берётся ближайшая точка стены — не просто
ближайшая точка облака, а ближайшая **из тех, что не позади** относительно
направления на цель (порог `back_ignore`). Это существенная деталь: без
фильтра, пройдя здание, дрон видит его сзади ближе, чем следующее спереди,
начинает вести уже пройденную стену и наматывает круги. Направление движения
складывается из касательной (перпендикуляр к направлению на ближайшую точку,
знак задаёт сторона обхода) и радиальной поправки, пропорциональной
`(r_min − clearance)`: подтягивает к стене, если далеко, отталкивает, если
близко.

### 3. За счёт чего исключены столкновения? Какой запас до препятствия и почему именно такой?

Столкновения исключаются тремя независимыми механизмами:

1. **Проверка коридора до входа в манёвр.** Дрон не начинает движение по
   прямой в занятое пространство: обнаружение срабатывает за 12 м, что при
   3 м/с даёт 4 секунды на реакцию.
2. **Активное удержание зазора при обходе.** Радиальная поправка — это
   пропорциональный регулятор, который непрерывно возвращает расстояние до
   ближайшей точки стены к `clearance`. Не «проверка на столкновение», а
   постоянное удержание дистанции.
3. **Ограничение скорости и сглаживание команды**, чтобы фактическая
   траектория не срезала углы относительно расчётной.

**Зазор `clearance` = 6 м** сложен из следующего:

| Составляющая | Оценка |
|---|---|
| Габарит дрона (Iris, полуразмах) | 0.3 м |
| Погрешность оценки положения EKF в SITL | ~0.5 м |
| Путь за один цикл управления при 3 м/с, 20 Гц | 0.15 м |
| Инерция: сглаживание + отработка автопилотом (~1–1.5 с) | ~3.5 м |
| Наклон корпуса в полёте (плоскость скана уходит от горизонта) | ~1 м |
| **Итого с округлением вверх** | **6 м** |

Основной вклад — инерция. Мультикоптер не меняет вектор скорости мгновенно:
между командой и реальным изменением направления проходит около секунды с
учётом сглаживания и работы контура автопилота, и на 3 м/с это уже 3 метра.
Прибавка на наклон корпуса нужна потому, что лидар закреплён жёстко: при
крене плоскость сканирования наклоняется, и оценка расстояния до
вертикальной стены становится оптимистичной.

Шесть метров — компромисс. Меньше 4 м на этой скорости уже опасно. Больше
8–10 м траектория становится неоправданно длинной, а на узких сценах дрон
перестаёт находить проходы. При изменении `cruise_speed` зазор нужно менять
пропорционально: он определяется в первую очередь тормозным путём.

`corridor_half` = 2.5 м — габарит дрона плюс запас на боковой снос; сознательно
меньше `clearance`, иначе дрон считал бы занятым коридор, вдоль стенки
которого он спокойно летит при обходе.

`max_range` = 15 м — обрезка дальномера. При наклоне корпуса дальние лучи
упираются в землю и выглядят как препятствие впереди; обрезка отсекает эти
ложные отражения, оставляя запас над `detect_dist`.

### 4. Как определяется застревание и как выполняется выход из него?

**Определение.** Застревание — это отсутствие **физического перемещения**:
за окно `stuck_time` = 10 с (модельного времени) дрон сместился в
пространстве меньше чем на `stuck_move` = 1.5 м.

Формулировка выбрана после ошибки. Первая версия детектора мерила сокращение
расстояния до цели — и срабатывала на каждом здоровом обходе, потому что при
движении вдоль стены расстояние до цели закономерно не уменьшается, это и
есть обход. Ложные срабатывания переворачивали сторону обхода, дрон разворачивался,
снова «застревал» — и наматывал круги у угла здания. То есть детектор сам
порождал то, что должен был лечить.

Вторая ошибка была в единицах времени: окно считалось по настенным часам, а
при RTF 0.3 десять реальных секунд — это три секунды полёта, за которые дрон
физически не может пройти полтора метра. Сейчас узел работает с
`use_sim_time: true`, часы Gazebo пробрасываются в `/clock`, и все окна
считаются в модельном времени. Это одновременно делает поведение независимым
от производительности машины, на которой запускается симуляция.

**Выход** — двухступенчатый:

1. **Увеличение зазора** на 1.5 м (с потолком `clearance + 4`). Помогает в
   типичном случае: дрон подошёл к стене слишком близко, и радиальная поправка
   борется с касательной составляющей.
2. **Смена стороны обхода** — каждое третье срабатывание. Это крайняя мера,
   потому что она ломает гарантию завершения Bug2: алгоритм требует
   фиксированной стороны, иначе теоретически возможно бесконечное
   переключение. Именно поэтому смена не делается сразу — сначала пробуем
   безопасный вариант.

Порог 10 с выбран с оглядкой на условие задания (провал — отсутствие
продвижения 10–15 секунд): детектор должен успевать вмешаться раньше, чем
сценарий признают непройденным, но не срабатывать на нормальных манёврах.
Развороты у угла здания занимают 3–5 секунд модельного времени, поэтому
десять — с двукратным запасом.

Отдельно: в фазе AVOID, когда стена уходит из поля зрения (все точки
позади), дрон **не зависает**, а продолжает движение к цели. Первая версия в
этой ситуации останавливалась и ждала данных — гарантированный провал по
критерию застревания.

### 5. Что произойдёт, если данные о препятствии пропадут в полёте? А если здание окажется больше ожидаемого или цель находится вплотную за ним?

**Пропажа данных лидара.** Работает watchdog: если с момента последнего
сообщения в `/scan` прошло больше `lidar_timeout` = 1.5 с, автомат переходит
в `FAILSAFE` — горизонтальная скорость обнуляется, высота удерживается.
Логика: без восприятия любое горизонтальное движение вслепую опаснее
остановки. Если данные восстанавливаются, полёт продолжается с фазы GO. Если
не восстановились за 5 секунд, отдаётся команда `RTL` — возврат на точку
взлёта средствами автопилота, который не зависит от бортового узла.

Это единственное место, где сознательно допускается зависание: оно
ограничено пятью секундами и заканчивается переходом в безопасный режим.

**Здание больше ожидаемого.** Не требует ничего — Bug2 не использует
априорных сведений о размере препятствия. Ведение границы продолжается,
пока не выполнится условие ухода, будь то 20 метров стены или 200. Реальные
ограничения — дальность лидара (стена должна оставаться в поле зрения) и
запас энергии. Дополнительно: у алгоритма нет предпочтения «короткой»
стороны, поэтому при неудачном выборе стороны обхода дрон может пойти вдоль
длинной стены. Выбор делается по одному скану в момент встречи и не
пересматривается.

**Цель вплотную за зданием.** Это известное слабое место реализации, и
честнее его назвать, чем замаскировать. Условие ухода с границы требует
`dist < hit_dist − leave_margin`, где `leave_margin` = 3 м. Если цель
расположена ближе к дальней стене здания, чем этот запас, условие может не
выполниться никогда: дрон обойдёт здание по кругу, вернётся в исходную точку
встречи и продолжит наматывать круги, пока не сработает детектор застревания
(тогда сменится сторона — что тоже не поможет).

Практические варианты: уменьшить `leave_margin` до 1 м (снижает
устойчивость к шуму скана — на выпуклом угле возможен преждевременный уход)
либо добавить проверку прямой видимости цели — если в направлении на цель
свободно на всю оставшуюся дистанцию, уходить с границы независимо от
`hit_dist`. Второй вариант правильнее, он и был бы следующим шагом.

**Цель внутри здания.** Недостижима. Bug2 в каноническом виде это
обнаруживает: дрон возвращается в точку встречи, не найдя условия ухода, и
может сообщить о недостижимости. В текущей реализации такая проверка не
сделана — сработает детектор застревания.

### 6. В каких системах координат выполняются расчёты и где происходят преобразования?

В цепочке участвуют четыре системы:

| Система | Где | Оси |
|---|---|---|
| Мировая Gazebo | сцена, положение зданий | ENU: x — восток, y — север, z — вверх |
| Локальная MAVROS | `/mavros/local_position/pose` | ENU относительно точки взлёта |
| Внутренняя ArduPilot | автопилот, MAVLink | NED: x — север, y — восток, z — вниз |
| Связанная (body) | лучи лидара | угол от носа дрона, против часовой |

**Все расчёты планировщика ведутся в локальной ENU MAVROS.** Это выбрано
сознательно: в ней же публикуется положение дрона и в ней же принимаются
команды скорости, поэтому преобразование нужно ровно одно — для лидара.

Преобразований по факту три:

1. **NED ↔ ENU** — выполняет MAVROS, прозрачно для узла. Планировщик с NED не
   работает вообще, и это устраняет главный источник путаницы со знаками.
2. **Body → ENU для лучей лидара** — в методе `points()` узла:
   `θ = yaw + angle_луча`, точка = позиция дрона + `r·(cos θ, sin θ)`.
   `yaw` извлекается из кватерниона `/mavros/local_position/pose`.
3. **Мировая Gazebo → локальная MAVROS** — не выполняется в коде, а
   обеспечивается совпадением начал: дрон взлетает из начала координат мира,
   поэтому обе ENU совпадают. Координаты зданий в `buildings.yaml` и цель в
   `mission.yaml` заданы в одних и тех же числах. Если сдвинуть точку спавна
   дрона, потребуется сдвиг и в конфиге целей — это ограничение, а не
   универсальное решение.

**Почему не используется tf2.** Преобразование одно, статическое (лидар
жёстко закреплён), и выражается тремя строками тригонометрии. Полноценное
дерево TF здесь добавило бы зависимость, точку отказа и задержку, ничего не
дав. В системе с несколькими датчиками и подвижными креплениями вывод был бы
обратным.

**Тонкость с наклоном.** Преобразование учитывает только `yaw`, но не крен и
тангаж. При наклоне корпуса в 10–15° плоскость сканирования отклоняется от
горизонтали, и лучи вперёд начинают уходить в землю. Строгое решение —
полный поворот кватернионом и отбраковка лучей с отрицательной вертикальной
составляющей. Здесь использовано более простое: обрезка дальности
(`max_range` = 15 м) плюс повышенная рабочая высота (8 м), при которых
земляные отражения не попадают в рабочий диапазон.

## Известные ограничения

Ограничения алгоритма:

- **Скан не кластеризуется на объекты.** Принадлежность точек зданиям не
  отслеживается; вместо этого используется эвристика «игнорировать точки
  позади». Работает на выпуклых препятствиях, разнесённых на расстояние
  больше `back_ignore`; на плотной застройке потребуется настоящая
  сегментация скана.
- **Узкие проходы.** Проход шириной меньше `2 × clearance` (12 м) дрон не
  пройдёт: он в него войдёт, но не сможет удержать зазор с обеих сторон.
  Проверки ширины перед входом нет.
- **Цель вплотную за препятствием** — см. вопрос 5.
- **Вогнутые препятствия.** Bug2 теоретически справляется, но длина обхода
  растёт, и детектор застревания может вмешаться раньше, чем алгоритм
  завершит манёвр.
- **Сторона обхода выбирается один раз** по одному скану и не
  пересматривается — возможен обход по длинной стороне здания.
- **2D-восприятие**: препятствия вне плоскости сканирования не видны.

Ограничения окружения:

- **RTF 0.16–0.35** в виртуальной машине из-за софтверного рендера сенсоров.
  Логика от этого не зависит (расчёты в модельном времени), но реальное
  время прогона в несколько раз больше модельного.
- **Точка взлёта совпадает с началом мира** — предполагается конфигурацией.

## Проблемы, с которыми пришлось разобраться

### Окружение

**Gazebo не запускался, пустой белый экран.** Движок Ogre 2 требует OpenGL
3.3+ core profile, а виртуальный адаптер VMware его не отдаёт. Решение —
`--render-engine ogre` (Ogre 1). Побочный эффект: не рендерится небо
(`Sky not supported by: ogre` в логах), на физику и сенсоры не влияет.

**`gpu_lidar` публиковал массив нулей.** Топик `/scan` существовал, но все
дальности были нулевыми — не `inf`, а именно нули, то есть буфер рендера
никогда не заполнялся. Причина: Ogre 1 поверх виртуального адаптера не
выполняет рендер лучей лидара. Ключ к решению — сервер Gazebo и GUI это
**разные процессы**, им можно задать разные движки:

- сервер: `--render-engine ogre2` + `LIBGL_ALWAYS_SOFTWARE=1` (софтверный
  llvmpipe поддерживает нужную версию GL, лидар считается корректно);
- GUI: `--render-engine ogre` на аппаратном ускорении, чтобы картинка не
  тормозила.

Попытка запустить сервер с аппаратным Ogre 2 приводила к загрузке GPU на 100%
и зависанию всей виртуальной машины.

### ArduPilot

**`PreArm: Motors: Check frame class and type`.** Параметр `FRAME_CLASS` был
равен 0 (тип рамы не задан), и библиотека моторов не инициализировалась. Дрон
армился и тут же разоружался. Решение — `sitl.parm` с `FRAME_CLASS 1` и
`FRAME_TYPE 1`, подключается через `--add-param-file`. Параметр применяется
только после перезагрузки автопилота.

**Ложное сообщение `Arming checks disabled`.** В ArduPilot 4.7 параметр
`ARMING_CHECK` переименован в `ARMING_SKIPCHK` с инверсией смысла (теперь это
маска проверок, которые нужно **пропустить**, 0 = все включены). MAVProxy
под новое имя не обновлён и печатает предупреждение по устаревшей логике.
Проверки при этом работают. Сообщение сбивало с толку при диагностике.

**`mavros_node` падал с `std::future_error: Promise already satisfied`.**
В launch был добавлен `--out 127.0.0.1:14550`, хотя `sim_vehicle.py` уже
пропускает MAVLink на этот порт. Два потока от одного аппарата — двойной
вызов `set_value()` на одном promise. Лишний флаг убран.

### Алгоритм

**Ложные срабатывания детектора застревания (версия 1).** Детектор мерил
сокращение расстояния до цели. При обходе стены оно закономерно не
уменьшается, поэтому срабатывание происходило каждые несколько секунд на
совершенно здоровом манёвре, и каждое переворачивало сторону обхода. Дрон
кружил у угла здания. Исправлено: детектор мерит **перемещение в
пространстве**, а смена стороны стала крайней мерой.

**Ложные срабатывания (версия 2).** Окна детектора считались по настенным
часам, а при RTF 0.3 они втрое короче в модельном времени, чем задумано.
Исправлено переводом узла на `use_sim_time` и пробросом `/clock` из Gazebo.

**Зависание при потере препятствия из виду.** В фазе AVOID при пустом облаке
точек узел останавливался и ждал данных — потенциально бесконечно, что по
условию задания означает провал. Исправлено: движение к цели продолжается,
счётчик прогресса продолжает работать.

**Дрон кружил вокруг первого здания (причина 1).** Условие ухода с границы
требовало, чтобы **весь** коридор до цели был свободен. При нескольких
зданиях следующее препятствие блокировало коридор, условие не выполнялось
никогда. Это было отступление от канонического Bug2, где уход зависит только
от m-линии и расстояния до цели. Исправлено: при проверке ухода
просматривается только ближняя зона (`clearance + 2`) — «не упираюсь ли я
прямо сейчас в стену, которую огибаю». Следующее здание обнаружится в фазе GO
и получит свою точку встречи, как и должно быть в Bug2.

**Дрон кружил вокруг первого здания (причина 2).** Ведомая стена выбиралась
как ближайшая точка облака вообще. Пройдя здание, дрон видел его сзади ближе,
чем следующее спереди, и начинал вести уже пройденную стену. Исправлено
фильтром точек, лежащих позади относительно направления на цель.

Обе последние ошибки — иллюстрация общего наблюдения: Bug2 элементарен,
когда известно, границу какого препятствия ведёшь. Лидар даёт безликое
облако точек, и вся сложность реализации сосредоточена в привязке этих точек
к объектам — а не в самом алгоритме.
